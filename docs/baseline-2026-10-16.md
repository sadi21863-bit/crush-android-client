## 7. Provider research — corrections to the roadmap

The roadmap recommends "Charm Hyper first" and warns *"do not guess `hyper`"*.
Researched from primary sources on 16 Oct 2026:

**`hyper` is real, and reading Catwalk's config directory would have hidden it.**
`internal/providers/configs/` has **no `hyper.json`** — only `opencode-zen.json`
among anything Zen/Charm-related. Crush registers it elsewhere,
`internal/config/load.go`:

```go
case catwalk.InferenceProvider("hyper"):
    if apiKey := env.Get("HYPER_API_KEY"); apiKey != "" {
```

So the authoritative facts:

| | |
|---|---|
| Provider id | `hyper` (plain) |
| Env var | `HYPER_API_KEY`, which takes precedence over config |
| API key prefix | `sk-hyper-` |
| Base URL | `https://hyper.charm.land/v1` |
| Catalogue | `GET /v1/models` → **HTTP 200, 22 models, no auth required** (measured) |
| Credit balance | `GET /v1/credits` → `{"balance": 100}` |
| Free allowance | "100 Hypercredits per month for free" |
| Documented errors | 401 and 5xx — **no 402/403 plan gate** |
| Compatibility | OpenAI-compatible, plus an Anthropic-compatible `/v1/messages` |
| Crush sign-in | **device-code flow**: "opens a browser tab… copy the device code back into Crush" |

Three consequences:

1. **The device-code flow is the answer to the OAuth blocker.** The roadmap
   assumed an app-link domain or a claimed loopback scheme was needed for
   redirect capture. A device code needs neither — the user types a short code
   into the app. That is implementable today, and it is how Crush's own TUI
   signs in.
2. **`normalizeApiKey` already handles `HYPER_API_KEY=sk-hyper-…`**, because it
   strips any `SCREAMING_SNAKE=` prefix. A key can be pasted verbatim.
3. **Hyper answers the Zen dead end.** Measured 11 Oct: a valid Zen key lists 43
   models and can call **none** (33 × 402, the ten `*-free` ids × 403). Hyper
   documents a free monthly allowance and has no plan gate. This is the single
   most consequential finding in this document.

The docs are served from `hyper.charm.sh`; the API and signup live on
`hyper.charm.land`. Both were reachable; the `.land` host is the API one.

`isKnown` for `hyper` is still **false** — no key has completed a handshake on a
device. Everything above is a verified *catalogue* fact, not a verified *chat*.

## 8. Open at this baseline

- **P0-02** unauthenticated loopback — not fixable in the app layer
- **P1-05** Stop not bound to an immutable run identity — next in line
- **P1-07** provider switch not serialised against an in-flight run
- **P1-04** no bounded readiness await before POST
- **P2-10** Zen-specific discovery in the generic provider path
- **`FALLBACK_PROBE_MODEL = "space-bunny-free"`** — that id is no longer in any
  catalogue, so it cannot even claim a workspace. Must go.
- **no root LICENSE**, no third-party notices
- **no Sigstore/cosign** verification of the engine download
- **`PATH=/system/bin`** — no git/python/node for the agent
- **one API key slot for all providers** — switching providers overwrites the
  previous provider's key. This is a real defect and it blocks using two
  providers, which is the normal case now that Zen is unusable.
