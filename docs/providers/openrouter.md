# OpenRouter (openrouter.ai) — Provider Research for Crush Mobile

*Researched 2026-10-17 from official sources only. Every claim carries its source inline. Anything not confirmable from a live official page today is marked **unverified**.*

## Summary

OpenRouter (OpenRouter Labs, Inc.) is a model aggregator: one OpenAI-compatible endpoint (`https://openrouter.ai/api/v1`) fronting ~469 model entries (live count 2026-10-17) from "80+ providers" (source: https://openrouter.ai/pricing; live count from https://openrouter.ai/api/v1/models). It is freemium: a plan table exists with a literal **Free plan** (payment options: "No") that includes "25+ free models" capped at 50 requests/day, and a Standard pay-as-you-go plan where buying credits raises the free cap to 1,000/day (source: https://openrouter.ai/pricing). Billing is prepaid credits with a 5.5% credit-purchase fee on Standard, no per-request markup over provider list price (source: https://openrouter.ai/docs/faq#pricing-and-fees). For Crush Mobile it is the cheapest end-to-end test path of all candidates: **signup → paste key → immediately chat on `:free` models, zero dollars, no card** (source: https://openrouter.ai/docs/faq#credit-and-billing-systems). The two app needs — SSE chat streaming and a dynamic list-models picker — are both first-class documented features (sources: https://openrouter.ai/docs/api_reference/streaming, https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties, verified live).

## Signup

- **What's required today:** create an account at https://openrouter.ai/sign-up, then create an API key at https://openrouter.ai/keys. The FAQ's official onboarding path is: "create an account and add credits on the Credits page. … Once you have credits you can either use the chat room, or create API keys and start using the API" (source: https://openrouter.ai/docs/faq). **No phone verification is mentioned anywhere in official docs** — checked the FAQ, quickstart, auth and limits pages; no mention. Phone **unverified** (not documented either way).
- **Email/OAuth specifics:** the docs do not spell out the identity-providers list on the sign-up form (it's a client-side app; the settings/credits page serves only an app shell to anonymous fetches). The system is Clerk-based: OpenRouter's own BYOK/datasets pages key member IDs on *"Clerk user IDs"* (source: https://openrouter.ai/docs/guides/overview/auth/byok) — Clerk means email + social login flows. Exact social providers: **unverified from docs**.
- **Key scoping — per-key credit limits:** keys are Bearer tokens; when you create one you "give it a name and choose a credit limit (or no limit). Once a key has used its credit limit, requests with it are rejected until you raise the limit … or, for a daily, weekly, or monthly limit, until the limit resets" (source: https://openrouter.ai/docs/api_reference/authentication). Keys created for you during onboarding get a **$100 credit limit and expire after 180 days** (same source). The exact per-key budget shape (`limit`, `limit_reset`, `limit_remaining`) is readable at `GET /api/v1/key` (source: https://openrouter.ai/docs/api_reference/limits). Official guidance: "We recommend setting a credit limit on every key" (source: https://openrouter.ai/docs/api_reference/authentication).
- **Programmatic key minting (nice for a client):** OpenRouter supports an OAuth PKCE flow at `https://openrouter.ai/auth?callback_url=…` that returns an authorization code, exchanged at `POST /api/v1/auth/keys` for a *user-controlled* API key — i.e., an app could, today, offer "Sign in with OpenRouter" and get the key without the user copy-pasting anything (source: https://openrouter.ai/docs/guides/overview/auth/oauth). The same page documents headless mode (code shown on screen, expires in 10 minutes). Not needed for v1 (paste-key flow works fine), but it is the documented integration path for client apps.

## Free tier

- **What `:free` means:** it is a *catalog variant* appended to a model slug; the free version appears as its own entry in the models API "with its own pricing, context length, and endpoints, and only models that list one support it" (source: https://openrouter.ai/docs/guides/routing/model-variants/free). Sibling variants: `:batch`, plus routing variants `:nitro`, `:floor`, `:exacto` (and deprecated `:online`) that don't get catalog entries (source: https://openrouter.ai/docs/faq#models-and-providers).
- **Free models that exist today** (live `GET /api/v1/models`, 2026-10-17 — 16 `:free` entries of 469 total). Exact current ids: `google/gemma-4-31b-it:free` (262,144 ctx; supports tools, reasoning, response_format), `google/gemma-4-26b-a4b-it:free` (262,144), `nvidia/nemotron-3-ultra-550b-a55b:free` (1,000,000), `nvidia/nemotron-3-super-120b-a12b:free` (262,144), `nvidia/nemotron-3.5-super-vl:free` (1,000,000), `nvidia/nemotron-3.5-lightning:free` (1,000,000), `thinkingmachines/inkling:free` (1,048,576), `thinkingmachines/inkling-small:free` (1,048,576), `dots-studio/dots-3-note-preview:free` (512,000), `cohere/north-mini-code:free` (256,000), `poolside/laguna-s-2.1:free` / `poolside/laguna-xs-2.1:free` (262,144), `xingchen-agi/xing4.0-29b-a4b:free` (262,144), `liquid/lfm-2.5-2.6b:free` (65,536), plus two niche nvidia policy/omni variants (source: https://openrouter.ai/api/v1/models, fetched 2026-10-17). Note the pricing page's claim "25+ free models" (source: https://openrouter.ai/pricing) doesn't match the live 16 — the catalog claim is marketing text and the live list is the truth.
- **Daily cap WITHOUT 💳 credits:** **50 free-model requests per day** (all-time credits purchased < $10) (source: https://openrouter.ai/docs/api_reference/limits; page exposes `FREE_MODEL_NO_CREDITS_RPD = 50`).
- **Daily cap WITH at least $10 purchased:** **1,000 free-model requests per day**, same 20/min per-minute cap (source: https://openrouter.ai/docs/api_reference/limits; `FREE_MODEL_HAS_CREDITS_RPD = 1000`, `FREE_MODEL_CREDITS_THRESHOLD = 10`). The exact threshold behavior: "the higher daily ceiling is granted starting one credit below the table's threshold (currently $9); an account that has purchased fewer credits than that reports `is_free_tier: false` together with the lower daily ceiling" (source: https://openrouter.ai/docs/api_reference/limits). The $10 threshold is confirmed on the pricing page: "rising to 1,000 per day once your account has bought at least **$10 of credits**" (source: https://openrouter.ai/pricing). So the historical 50→1,000 change is **current**: 50/day without, 1,000/day with.
- **Per-minute cap:** **20 requests/minute for `:free` variants, both tiers** (source: https://openrouter.ai/docs/api_reference/limits, `FREE_MODEL_RATE_LIMIT_RPM = 20`). For paid models there is "no plan-based rate limit… limits on paid models come from the provider" plus generic DDoS protection (source: https://openrouter.ai/pricing#faq).
- **Concurrent-request cap:** there is **no documented fixed concurrent-request number today**. OpenRouter governs "capacity globally" — creating extra accounts or keys does not raise limits (source: https://openrouter.ai/docs/api_reference/limits). In its place there is an **in-flight spending budget**: for small-balance and newer accounts, the estimated token cost of running/recently-settling paid requests is held against the balance up to a fraction of the balance (with a ceiling), and 402s carry `reason: "in_flight_budget_exhausted"`; free-model requests are explicitly exempt from this budget (source: https://openrouter.ai/docs/api_reference/limits). The old fixed "concurrent requests" figure appears nowhere in the current docs; any specific number would be **unverified**.
- **Failed attempts and negative balance:** "Failed attempts count toward that daily cap, and a negative balance blocks free models until you add credits" (source: https://openrouter.ai/pricing#faq); the limits page confirms 402s can occur "including for free models" when the balance went negative (source: https://openrouter.ai/docs/api_reference/limits).
- **Monitoring the cap from the app:** `GET /api/v1/key` returns `free_model_daily_requests: {used, limit, remaining}` plus `is_free_tier` and all per-key/credit figures — a perfect client-side quota display (source: https://openrouter.ai/docs/api_reference/limits).
- **Free auto-router:** model id `openrouter/free` "automatically select[s] a free model" — useful fallback slug when a specific `:free` id dies (source: https://openrouter.ai/docs/faq#credit-and-billing-systems).

## Pricing

- **Free starting allowance:** "All new users receive a small free allowance to test out OpenRouter" (source: https://openrouter.ai/docs/faq#credit-and-billing-systems). The FAQ doesn't quantify it in dollars; in practice the meaningful $0 path is the free `:free` models, which require no credits at all. Exact grant size: **unverified**.
- **How paid usage works:** prepaid credits denominated in USD; every request's token cost is deducted from the balance; manual top-up or "auto top up" when the balance drops below a threshold (source: https://openrouter.ai/docs/faq#credit-and-billing-systems). Pricing per model passes through the underlying provider's list price; "there is no markup on inference pricing (however we do charge a fee when purchasing credits)" (same source).
- **The fee:** "OpenRouter charges a 5.5% ($0.80 minimum) fee when you purchase credits"; crypto payments are charged 5% (source: https://openrouter.ai/docs/faq#pricing-and-fees). The plan table shows the same 5.5% on Standard, and 8% on the Business tier (source: https://openrouter.ai/pricing).
- **Minimum top-up:** no official page I could fetch today states a minimum credit-purchase amount. The pricing FAQ says Standard has "no minimums and no lock-in" (source: https://openrouter.ai/pricing#faq) and the only dollar figure tied to purchases is the $0.80 minimum *fee* (source: https://openrouter.ai/docs/faq#pricing-and-fees). The historically documented $5 minimum is **unverified today** (the settings/credits page requires sign-in and serves no content to anonymous requests). Treat the real minimum as "a few dollars" until verified in the buy flow.
- **Payment methods:** "all major credit cards, AliPay and cryptocurrency payments in USDC" (source: https://openrouter.ai/docs/faq#credit-and-billing-systems); the plan table's Free plan row reads **"Payment options: No"** (source: https://openrouter.ai/pricing). Refunds: unused credits within 24h of purchase, fees non-refundable, crypto never refundable (source: https://openrouter.ai/docs/faq#credit-and-billing-systems). Credits don't auto-expire but OpenRouter "reserve[s] the right to expire unused credits after one year of purchase" (same source). Failed/fallback attempts are not billed for model tokens ("Zero Completion Insurance") (source: https://openrouter.ai/pricing#faq).
- **BYOK cost:** bringing your own provider key is free under a "$25,000 of list price inference / month with no fees, 5% fee after" allowance on Standard (source: https://openrouter.ai/pricing; details at https://openrouter.ai/docs/guides/overview/auth/byok).

## API compatibility

- **Base URL & endpoints:** `https://openrouter.ai/api/v1`; chat at `POST /api/v1/chat/completions`; models at `GET /api/v1/models`. "OpenRouter implements the OpenAI API specification for /completions and /chat/completions" (source: https://openrouter.ai/docs/faq#api-technical-specifications), and it is explicitly a drop-in for the OpenAI SDK (`baseURL: https://openrouter.ai/api/v1`) (source: https://openrouter.ai/docs/api_reference/overview). There are also OpenAI-Responses-style and an Anthropic-Messages-style surface (`/api/v1/responses`, `/api/v1/messages`) per the OpenAPI tag list (source: https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties — the shared OpenAPI spec it embeds).
- **Auth:** `Authorization: Bearer <OPENROUTER_API_KEY>` (source: https://openrouter.ai/docs/api_reference/authentication). Our app's "bare key" storage approach ports over fine: OpenRouter wants the raw key Bearer-token style, exactly like our `CrushApi.setProviderKey` normalization already produces.
- **Chat request schema:** full TS schema is documented; OpenAI-compatible fields plus OpenRouter-only ones: `models?: string[]` (fallback list), `route?: 'fallback'`, `provider?: ProviderPreferences`, `plugins?: Plugin[]`, `user?: string` (abuse detection) (source: https://openrouter.ai/docs/api_reference/overview). If the chosen model doesn't support a parameter, "the parameter is ignored" rather than rejected (same source). Structured outputs via `response_format` + assistant prefill are supported (same source).
- **Streaming (SSE):** set `stream: true`; the SSE stream "will occasionally contain a 'comment' payload" — lines like `: OPENROUTER PROCESSING` keep-alives that must be skipped before JSON.parse or the parse loop crashes (source: https://openrouter.ai/docs/api_reference/streaming — verified to exist exactly as our Crush SSE parser structurally allows; OpenRouter comments are simpler than Crush's republished-message model since only `data:` lines carry JSON here too). Two subscription-critical deviations from OpenAI:
  - The final usage chunk "intentionally deviates": it contains **one choice with a content-free delta repeating the finish_reason** (OpenAI's spec uses an empty `choices` array) — clients that index `choices[0].delta` unconditionally are fine; clients that skip chunks with empty `choices` arrays should still handle the extra terminal-looking frame (source: https://openrouter.ai/docs/api_reference/streaming).
  - **Mid-stream errors arrive as `data:` events with a top-level `error` field and `choices[0].finish_reason: "error"` under an already-sent 200**, and "the error can be the first and only event in the stream, so treat a `200` carrying an `error` chunk with no content as a failure, not a success" (source: https://openrouter.ai/docs/api_reference/streaming). This is identical in spirit to our Crush `finishError` discipline.
  - `X-Generation-Id` response header for correlation; stream cancellation by aborting the connection works only for a documented subset of providers (source: same).
- **List-models shape (picker data):** `GET /api/v1/models` is **public — no API key required** ("the `pricing` object on each model, no API key required", source: https://openrouter.ai/pricing#per-model-prices; verified live today without auth). Each entry carries: `id`, `canonical_slug`, `name`, `context_length`, `pricing { prompt, completion, request, image, … }(strings, USD/token)`, `supported_parameters[]` (includes `tools`, `tool_choice`, `response_format`, `reasoning`…), `top_provider { context_length, max_completion_tokens, is_moderated }`, `architecture { modality, input_modalities, output_modalities, tokenizer }`, `created`, `expiration_date`, `benchmarks`, `reasoning`, `per_request_limits` (source: https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties, OpenAPI schema in-page; shape confirmed against live output for `google/gemma-4-31b-it:free`).
- **Server-side picker filters:** `max_price=0` + `max_output_price=0` returns the free list (verified live: 18 rows today — slightly more than the 16 `:free` ids, i.e. it can include zero-priced non-suffixed entries), plus `supported_parameters=tools`, `q <search>`, `context`, `min/max_age_days`, `min_intelligence_index`, `min_tool_success_rate`, and `sort=pricing-low-to-high|newest|most-popular|top-weekly|intelligence-high-to-low|…`; pagination `offset/limit` defaults to full list, max page 1000 (source: https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties; filters executed live today). Per-model endpoint detail is at `GET /api/v1/models/{id}/endpoints` (source: same page — `links.details`).
- **Tool calling passthrough:** `tools`/`tool_choice` "will be passed down as-is for providers implementing OpenAI's interface. For providers with custom interfaces, we transform and map the properties" (source: https://openrouter.ai/docs/api_reference/overview). With tools present OpenRouter makes a best effort to route only to providers supporting tool use (source: https://openrouter.ai/docs/guides/routing/provider-selection). The free variant we inspected ships `tools` + `tool_choice` in `supported_parameters` (live check 2026-10-17).
- **Provider routing params:** the request-level `provider` object accepts `order: string[]`, `allow_fallbacks`, `require_parameters`, `data_collection: "allow"|"deny"`, `zdr: boolean`, `only: string[]`, `ignore: string[]`, `quantizations: string[]`, `sort: "price"|"throughput"|"latency"` (or `{by, partition}`), `preferred_min_throughput`, `preferred_max_latency`, `max_price` (source: https://openrouter.ai/docs/guides/routing/provider-selection). Model-level fallback lists go in the `models: []` array (with optional `provider.sort.partition: "none"` to rate-optimize across models), documented under Model Fallbacks (source: https://openrouter.ai/docs/guides/routing/provider-selection#advanced-sorting-with-partition). Auto-fallback across providers on 5xx/rate-limits is default-on (source: https://openrouter.ai/docs/faq#models-and-providers).

## Data-use policy

- **OpenRouter itself:** "Prompt and completion are not logged by default. We do zero logging of your prompts/completions, even if an error occurs, unless you opt-in", and "OpenRouter has never shared, sold, or licensed underlying prompt data to any third party" (source: https://openrouter.ai/docs/faq#privacy-and-data-logging; expanded at https://openrouter.ai/docs/guides/privacy/data-collection). Two opt-in logging toggles exist (observability logging for your own dashboard; OpenRouter product-improvement use for a 1% usage discount), both off by default (source: https://openrouter.ai/docs/guides/privacy/data-collection).
- **Upstream training — the mechanism:** each listed provider has a recorded data policy ("May train" / "Does not train" / retention days; the live table is fetched in the doc page itself from OpenRouter's `all-providers` API) (source: https://openrouter.ai/docs/guides/privacy/provider-logging). "There are **separate settings for paid and free models**" for allowing routing to providers that may train (source: same page). For free routes specifically: "Providers that do log, or where we have been unable to confirm their policy, will not be routed to unless the model training toggle is switched on in the privacy settings tab" (source: https://openrouter.ai/docs/faq#privacy-and-data-logging). Practical read: **a default-state account is already opted out** of training providers on free models; enabling the free-model training toggle is what unlocks the "fully-scraped" free routes.
- **The exact setting:** account-wide, per-model-group and free/paid — in the UI at `https://openrouter.ai/settings/privacy` (linked repeatedly as "your privacy settings") (source: https://openrouter.ai/docs/guides/privacy/provider-logging). Per-request override: `provider.data_collection: "deny"` (only providers that "do not collect user data") or `"allow"` (default) (source: https://openrouter.ai/docs/guides/routing/provider-selection#requiring-providers-to-comply-with-data-policies). Stricter still: `provider.zdr: true` restricts to zero-data-retention endpoints (source: same).
- **Documented tradeoff when opted out:** "If you specify provider routing in your request, but none of the providers match the level of privacy specified in your account settings, you will get an error and your request will not complete" (source: https://openrouter.ai/docs/faq#privacy-and-data-logging); the failure surfaces as **HTTP 503 "No available model provider meets your routing requirements. Consider relaxing provider preferences or adding fallback models."** (source: https://openrouter.ai/docs/api_reference/limits, status-code table). So a `:free` id whose only upstream is a training-provider can 503 for opted-out accounts — the app must present this error as "free route unavailable under your privacy setting", not as a crash.
- **BYOK carve-out:** adding your own provider key does *not* bypass the policies — data-collection and ZDR restrictions still apply to BYOK endpoints (source: https://openrouter.ai/docs/guides/overview/auth/byok).

## Gotchas

1. **Model ids churn and die.** Each catalog entry has a documented `expiration_date` ("the date after which the model may be removed") and deprecated models return **404 with "no endpoints for this model found"** (source: https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties; https://openrouter.ai/pricing#faq). `:free` variants rotate the most — the free roster today (NVIDIA Nemotron / Gemma-4 / Thinking Machines etc.) looks nothing like the 2025 free roster; the pricing page's static "25+ free models" already disagrees with the live 16 (source: https://openrouter.ai/pricing vs https://openrouter.ai/api/v1/models, 2026-10-17). **Never hardcode a picker; always hydrate from the models API.**
2. **The free cap counts failures:** failed attempts count toward the 50/day cap, and a negative balance blocks even free models until credited (source: https://openrouter.ai/pricing#faq; https://openrouter.ai/docs/api_reference/limits). A burst of malformed requests can burn the whole day's quota.
3. **429 shapes differ by source:** a platform 429 is `{error:{code:429,message:"Rate limit exceeded",metadata:{error_type:"rate_limit_exceeded"}}}` with `X-RateLimit-Limit/Remaining/Reset` headers — but "Successful inference responses do not include X-RateLimit-* headers"; a provider-side 429 arrives after fallback routing with `error.metadata.provider_code` carrying the upstream code; and once a stream starts, a 429 arrives as an SSE event with `finish_reason:"error"` instead of HTTP 429 (source: https://openrouter.ai/docs/api_reference/limits). Also honor `Retry-After` when present (same source).
4. **402s have a three-way taxonomy:** `limit_source: openrouter_credits` (balance) vs `openrouter_key_limit` (key cap) vs `openrouter_in_flight_budget` (transient hold exhaustion, retryable per `Retry-After`) — branch on `metadata.limit_source`, not on message text (source: https://openrouter.ai/docs/api_reference/limits).
5. **BYOK is not free for us and costs a fee above allowance:** prioritized keys are tried first by default, 5% fee beyond $25,000/month of list-price inference on Standard; keys per provider support model/key/member filters and "never use shared capacity" modes (source: https://openrouter.ai/docs/guides/overview/auth/byok; https://openrouter.ai/pricing). Low relevance for a free-tier flow, but cite the 5% figure if we ever expose BYOK.
6. **Onboarding-minted keys expire:** keys created during onboarding get a $100 limit and expire after 180 days — a stale-key failure mode unique to OpenRouter (source: https://openrouter.ai/docs/api_reference/authentication). Detect via 401 → prompt re-key.
7. **Multiple accounts don't scale limits:** "Making additional accounts or API keys will not affect your rate limits, as we govern capacity globally" (source: https://openrouter.ai/docs/api_reference/limits) — round-robin account farming is explicitly written off.
8. **Free routes have a moderation flag:** `top_provider.is_moderated` exists per model (e.g. `google/gemma-4-31b-it:free` reported `is_moderated: false` today, source: https://openrouter.ai/api/v1/models) — a picker can filter or label moderated free routes for user transparency.
9. **Coinbase programmatic top-up is dead:** `POST /api/v1/credits/coinbase` returns 410 Gone; purchases are web-flow only now (source: https://openrouter.ai/docs/cookbook/administration/crypto-api).

## Verdict for Crush Mobile

**Yes — OpenRouter is the easiest $0 end-to-end test path available to a new user today.** Signup is account-only (no card, and no phone step documented — email/social via a Clerk-based app), and free `:free` chat models require *no credits whatsoever*: a brand-new user with a $0 balance can create a key at `openrouter.ai/keys` and immediately run `POST /api/v1/chat/completions` against ids like `google/gemma-4-31b-it:free` or `nvidia/nemotron-3-ultra-550b-a55b:free` within a documented budget of **20 requests/minute and 50/day**, instantly checkable in-app via `GET /api/v1/key`'s `free_model_daily_requests` (sources: https://openrouter.ai/docs/api_reference/limits, https://openrouter.ai/docs/api_reference/authentication, live `/api/v1/models` pull 2026-10-17). What they get for free is genuinely chatting (16–18 free model choices, several with 256K–1M contexts and tool support) — but rate-limited for testing scale, not production ("usually not suitable for production use", source: https://openrouter.ai/docs/faq), subject to free-roster churn (picker must be dynamic — our existing Zen live-models pattern maps 1:1 because OpenRouter's `/api/v1/models` is public, filterable server-side with `max_price=0`, and requires no auth), and — crucially for an on-device agent — free routes sit behind a free-vs-paid privacy toggle at `settings/privacy`: by default OpenRouter routes free traffic only to no-training providers, and requesting a free model whose only upstream trains yields a documented 503/abort (sources: https://openrouter.ai/docs/guides/privacy/provider-logging, https://openrouter.ai/docs/faq). Integration cost for us is minimal: OpenAI-compatible schema, Bearer key, SSE with skip-`:`-comment and an in-band `finish_reason:"error"` failure frame our streaming code already models. Recommended posture: support OpenRouter as a pasted-key provider, hydrate the model picker from `GET /api/v1/models?max_price=0` (with `:free`-suffix filtering as a belt-and-suspenders), surface `free_model_daily_requests` and `is_free_tier` in settings, and treat `$10 top-up` as the documented magic number that unlocks the 1,000/day tier — the same price point at which every other provider in our evaluation also becomes usable.
